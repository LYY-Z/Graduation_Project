# 第 11 节：真实机器人代码路径

## 本节要回答的问题

模拟器里的策略怎样连接到真实相机、机器人和控制器？本节只解释仓库代码的结构和数据流，不代表环境已经连上机器人，也不构成硬件操作指南。

真实机器人控制可能造成设备损坏或人身风险。未经设备负责人指导、急停/限位检查、速度和工作空间限制、人员隔离及安全测试，不要运行真实机器人评估脚本。

## 1. 模拟与真机的共同部分

两者共享策略本身的主要概念：

~~~text
观测 O_t → 策略 predict_action() → 动作计划 → 执行其中一段
~~~

变化的是“观测从哪里来”和“动作由谁执行”：

| 环节 | 模拟任务 | 真实机器人 |
|---|---|---|
| 图像/状态 | 环境直接返回 | 相机与机器人状态采集进程提供 |
| 动作执行 | env.step(action) | 控制器按时间戳发送目标位姿/动作 |
| 时间 | 环境步进 | 相机帧与机器人反馈有真实延迟 |
| 安全约束 | 仿真边界 | 急停、限位、速度、碰撞和人员安全 |

## 2. 真实观测需要对齐

真实系统里的相机帧和机器人状态不是数学上同一时刻自动产生的。RealEnv 一类模块会根据时间戳收集并对齐观测，整理成策略期望的字段，例如图像和末端/夹爪状态。

随后还需与训练一致地进行图像尺寸、通道顺序、历史帧堆叠和状态字段组织。若训练用的 key/shape 与真机传入的不一致，模型可能无法运行；更危险的是字段虽能拼上但语义或单位不同，导致动作错误。

## 3. 动作计划到控制器

策略动作一般是模型计划中的相对或绝对控制量。真机接口负责把策略输出转换成控制器认可的目标，例如工作空间中的位姿和执行时间。代码可能采用：

1. 根据 observation 计算动作计划；
2. 将动作映射为带时间戳的 waypoint；
3. 交给异步/插值控制器按时执行；
4. 同时采集新的相机和机器人状态；
5. 到达重规划时刻后再次调用策略。

RTDEInterpolationController 一类控制组件可能在独立进程中与 UR 控制接口通信，并对目标位姿做时间插值。策略并不直接“控制电机电流”；策略和底层控制器分层，各自处理不同时间尺度的问题。

## 4. 记录演示与策略评估是两条用途不同的路径

- demo_real_robot.py 一类程序用于人工遥操作/示教和数据记录，常用 SpaceMouse 等输入装置。
- eval_real_robot.py 一类程序用于加载训练好的策略，在真实环境中循环观察、推理和执行。

示教程序产生/记录训练数据；评估程序消费策略权重并执行控制。不要把“可以采数据”误认为“已经训练好策略”，也不要把模拟评估脚本当成真机脚本。

## 5. 异步进程、共享内存与时间戳

图像采集、机器人反馈、策略计算和动作控制可能同时运行。进程间共享内存/队列用于传递数据，时间戳用于判断新旧和对齐。它们的作用是让实时数据流更可靠，并减少把慢速策略计算直接塞进底层伺服循环的风险。

初读时只抓住接口边界：

~~~text
相机/机器人进程 → RealEnv 组织观测 → policy 推理
              → 控制器接收目标 → 机器人执行并产生新状态
~~~

遇到具体延迟、缓冲区或控制频率问题，再分别读 real_world/、shared_memory/、timestamp_accumulator.py 和控制器实现。

## 6. 真机代码学习顺序与安全边界

建议先确认模拟策略的 predict_action()、动作单位、归一化与切片，再读真机 observation/action adapter，最后阅读控制器。首次理解真机代码时优先做静态阅读或 mock/离线检查。

实际运行前必须由熟悉设备的人确认：机器人型号和坐标系、末端工具、工作空间、动作尺度、控制频率、急停、人员位置、网络连接和场景障碍。此文档不提供自动越过这些安全检查的许可。
