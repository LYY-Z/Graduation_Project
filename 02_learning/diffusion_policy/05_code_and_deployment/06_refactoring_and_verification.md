# 06 重构改变了什么，以及哪些结论有证据

本章把“目录变了”“代码能安装”“离线测试通过”和“实机能完成任务”分开解释。前五章教你理解程序；这一章教你判断程序的变化是否可信，以及以后怎样向团队或论文读者说明这些变化。

先记住本次的范围：旧工程保留，新工程是另一个目录；没有登录服务器，没有启动相机或机械臂，没有在本地反序列化 checkpoint 或执行真实神经网络推理。所有实机数字来自旧工程已留存的那一次短测。

## 1. 为什么要先复制，而不是在旧目录里搬文件

旧工程包含两类东西：一类是代码，另一类是“这些代码曾经跑过”的事实依据。源代码版本、参数、模型、控制后端和运行日志共同组成一条证据链。直接在旧目录改名和合并以后，旧日志仍在，但它对应的代码已经变了，之后就容易把不同版本混在一起。

本次保留：

- 重构前工程当前保存位置：`G:/毕设/03_code/diffusion_policy_ur7e_v1`。
- 模块化工程当前保存位置：`G:/毕设/03_code/diffusion_policy_ur7e`；重构记录中曾使用`diffusion_policy_ur7e_refactored`名称。
- 学习材料：当前 `02_learning/diffusion_policy/05_code_and_deployment`。
- 验证材料：本目录的 `verification/`。

复制前记录了 1138 个非缓存文件的 SHA-256，然后校验复制结果。这个数字包含原始资料和第三方文件，不代表有 1138 个我们手写的业务文件。Git 内部记录、Python 环境、缓存和字节码不属于这份比较清单。

SHA-256 可以理解为对文件内容计算的一串指纹。改一个字符通常就会得到不同指纹。它能帮助检查“内容有没有变”，但不能说明内容本身一定正确，也不能替代现场安全检查。

对应记录是 [original_snapshot.json](verification/original_snapshot.json)。交付时的再次核对结果见 [acceptance.json](verification/acceptance.json)。不要手工编辑这些文件来使数字“看起来一致”。

## 2. 文件减少和职责清楚，分别是什么意思

“模块化”不是让目录越深越好，也不是让文件越少越好。这里采用三组职责：硬件、推理、控制；共用的流程、几何、配置和记录放在包根目录。

| 原文件 | 新位置 | 调整理由 |
|---|---|---|
| images.py、frame_store.py | hardware/camera.py | 都围绕图像数组和跨进程帧交换 |
| camera_bridge.py | hardware/camera_bridge.py | ROS 节点仍是独立进程边界 |
| robot.py | hardware/robot_state.py | 文件名明确表示只读状态，不是运动控制 |
| observations.py、session.py | hardware/observations.py | 采样生命周期、历史和两帧配对围绕同一份观察 |
| model.py | inference/policy.py | 把模型加载与统一预测包装放在一起 |
| runner.py、execution.py 中的流程 | pipeline.py | 统一编排和公共步骤，避免两份预测实现 |
| motion_safety.py | control/safety.py | 纯数值目标过滤，与发送指令分开 |
| motion_robot.py、guarded_backend.py | control/robot.py | 统一真实控制边界和其私有后端验证 |
| geometry.py | geometry.py | 输入位置和输出目标都要用的纯几何 |
| config.py、recording.py | 同名公共模块 | 配置和记录不属于某一种硬件 |

`pipeline.py` 是流程组织者，不负责重新实现扩散算法、ROS 图像解码或底层网络传输。可以把它看成一份按顺序调用其他模块的工作流程：取得观察、调用模型、处理结果、在指定模式下执行、记录、退出。

`hardware/robot_state.py` 与 `control/robot.py` 分开尤其重要。前者有能力读取状态，后者才包含创建控制客户端和发送指令的功能。文件导入和对象创建也分开处理：读到一个类定义，不等于已经创建了与机器人相连的对象。

常规的 `__init__.py` 用于包标识，`__main__.py` 用于 `python -m dp_ur7e` 入口。把这些常规文件算进去，文件总数当然多于十二；“十二个业务文件”是在说明需要重点理解的功能数量。

## 3. 重新整理过的接口与旧实现有什么不同

### 3.1 一套命令描述六种模式

旧工程的 capture/shadow 与实机执行入口分开。新工程统一为：

```text
inspect → 文件与配置检查
camera-bridge → 接收 ROS 图像，写最新帧
capture → 构造并保存一份真实观察
shadow → 真实观察输入模型，只记录预测
preview → 还计算限幅后的候选，不创建运动控制客户端
execute → 经过明确条件检查后执行受限目标
```

同一个入口使“当前到底在哪一阶段”更清楚。它不意味着所有阶段都会自动串行执行。尤其是 `camera-bridge` 仍需单独进程运行，驱动也需要在项目外启动。

`--site-ready` 只允许用于 `execute`。给 `shadow` 加这个参数会报错，而不会悄悄变成执行模式。选择 `execute` 时缺少该参数，也会在读配置和加载设备之前被拒绝。

### 3.2 公共配置模板与现场配置分开

公共仓库提交 `config.example.yaml`。现场使用者复制为被 Git 忽略的 `config.yaml`，填写设备和路径，并完成现场 TCP 核验。示例中的 `192.0.2.1` 是文档地址，不是可直接操作的机器人地址；硬件模式会拒绝它。

新配置使用 schema_version 2，写明实现为 guarded、默认模式为 preview。它不再使用旧的“execution implementation absent”字面描述；真正是否允许动作仍由命令模式、现场声明和执行前检查共同决定。

配置中的 `project_root` 相对配置文件所在目录解释，不相对终端当前目录猜测。原版代码、模型、帧文件、运行结果的路径都要在项目内。这样换一台机器、换一个项目目录后，不应再依赖某位开发者的绝对路径。

### 3.3 只有一份公共预测包装

原来 shadow 和实机流程各自有一段“NumPy 转 Tensor、调用 predict_action、转回 NumPy”的代码。现在统一调用 `inference.policy.predict`。

这不是把原算法换成另一个算法。原版 Transformer、ResNet、normalizer、EMA 参数和 DDPM 调度器仍由固定上游和官方 checkpoint 提供。包装层处理的是输入输出格式和调用方式。

shadow 的耗时记录现在覆盖公共包装中的转换和可选 CUDA 同步。它与旧 shadow 计时边界略有区别。因此以后比较速度时，需要先保证计时定义一致；不要把实现整理造成的计时边界变化写成算法加速。

## 4. 哪些核心实现保留不变

本次没有调整以下内容：

- 原论文源码版本、官方模型权重及其内置 normalizer。
- RGB/BGR 解码、行跨度处理、中心裁剪、96×96 缩放和 CHW 数组转换。
- 两帧观察、因果状态配对、三种时钟的区分和旧数据拒绝逻辑。
- 相对锚点平面映射，以及它“未标定”的能力边界。
- 使用 `action[0,0]` 作为当前候选，然后重新观察和推理。
- 实际执行选用的 `MotionLimits.visible()` 数值。
- 目标检查、反馈检查、稳定 ready 等待、发送前再次检查新鲜度。
- ACK 与物理到位的区分、连续反馈确认、失败停止和资源清理。
- 私有 SDK 的不自动重连、不重放旧动作及即时发送失败语义。

这里“实际执行的限制”与 `MotionLimits()` 的类默认值要区分。默认构造保留了更严格的早期微动配置；实际 `run_execution` 明确选择 `visible()`：单条 1 mm、累计路径和包络 3 mm、速度 2 mm/s、加速度 5 mm/s²、平滑系数 0.5、最多三条命令。看数值时应看本次实际选用并写入元数据的那组，而不是只看到类定义的第一行。

私有 SDK 的源码目录已经包含受限补丁。`guarded.patch` 用于展示相对原始 SDK 的修改依据，不是让操作者对当前源码再应用一次。重复应用会失败或造成错误。对应状态写在构建配置和来源清单中。

## 5. 验证分成哪些层，为什么不能互相替代

| 验证层 | 本次做了什么 | 能说明什么 | 不能说明什么 |
|---|---|---|---|
| 文件与来源 | 校验官方源码、SDK 和权重 | 输入版本与预期一致 | 模型在真实任务上有效 |
| 语法与风格 | Python 解析、Ruff 检查和格式化 | 可以解析，常见代码问题未出现 | 程序逻辑全部正确 |
| 回归测试 | 原有测试迁移后继续执行 | 已有数值与边界规则仍符合断言 | 未覆盖的现场状态一定正常 |
| 差分比较 | 同样数字输入同时喂旧实现和新实现 | 两者在这些输入上输出一致 | 对所有可能输入都形式化等价 |
| 离线集成 | 合成观察、替代模型与设备接口走真实流程 | 模块衔接和状态流可以连起来 | 实际网络、GPU、相机或机器人正常 |
| 包构建 | 构建 wheel，检查其内容与导入 | 适配包可以被打包和加载 | 第三方资源已自动包含在 wheel 中 |
| 实机验收 | 当前未执行 | 无新增实机结论 | 不能据此说新版已实机跑通 |

这张表是以后汇报时最有用的一张表。别人问“你测试了吗”，应该回答具体是哪一层、使用什么条件、得到什么结果，而不是只回答“测过了”。

### 5.1 为什么会看到“测试通过，但有跳过”

本机不具备 ROS 系统运行环境，因此五个相机生命周期测试被明确标为 skipped。跳过意味着没有运行，不能当作通过。它们并没有被删除；到了相应 ROS Python 环境仍应单独执行。

原基线是 105 项通过、5 项跳过。新增测试覆盖统一命令、导入副作用、配置、发布文件、候选后端激活和离线集成。最终结果以 [final_tests.txt](verification/final_tests.txt) 和 [acceptance.json](verification/acceptance.json) 为准。本章不把 GitHub CI 工作流“已经写好”说成“已在 GitHub 运行通过”。

### 5.2 38 个定义结构一致是什么意思

程序可以被解析成语法树。换行、空格和排版不同，树仍可能相同。本次对照了图像处理、帧交换、几何、观察历史、过滤器、反馈确认等 38 个关键定义，去掉位置属性以后语法树一致。

这比“肉眼看起来差不多”更精确，但不是完整等价证明。导入了哪个模块、数据来自哪里、文件路径指向什么，也会影响运行。因此还要做路径检查、导入检查、数值比较和集成测试。

记录见 [equivalence.json](verification/equivalence.json)。其中还说明了主动改变的部分：模块路径、配置和命令接口、统一预测包装的计时边界，以及后端清单验证。

### 5.3 533 组差分比较在比较什么

比较使用同一套本地 NumPy/OpenCV 环境和固定随机种子，分别调用旧函数与新函数，检查：

- 带行填充的 RGB/BGR 解码结果。
- 不同尺寸图像的裁剪、缩放和张量结果。
- 多组 TCP 到二维位置、二维位置到 TCP 的转换。
- 多次限幅、平滑、提交预算后的目标和状态。
- 两帧图像与状态配对后的观察数组和证据字段。

533 是检查案例数量，不是 533 次真实机械臂实验，也不是统计学上的任务成功率。

## 6. 离线“完整流程”怎样测试，又替代了哪些东西

测试文件是 [test_pipeline_offline.py](../../../03_code/diffusion_policy_ur7e/tests/test_pipeline_offline.py)。

它使用真正的 ObservationHistory 构造两帧观察，用真正的公共 Tensor 包装接口调用一份替代策略。替代策略返回形状正确的二维动作数组；后续映射、ActionGuard、GuardedRobot 的检查、完成状态判定和 RunWriter 落盘都使用实际项目实现。

设备边界的替代对象会：

- 返回正常机器人模式、一致的时间戳、位姿和关节值。
- 接收 moveL 调用，保存目标，并模拟状态已经移动到该目标。
- 返回变化后的异步完成标记。
- 支持停止和断开，使清理路径也能被断言。

另外，Windows 没有 fcntl，因此该测试只在锁这个操作系统边界使用替代上下文。真实 Linux 文件锁仍需在目标环境验证。

这个测试的价值是：假如重构后函数参数不匹配、输出形状传错、过滤结果没有交给执行器，或者预演错误地创建控制连接，测试就可能失败。它不包含物理惯性、接触、线缆、控制器固件、网络延迟或神经网络计算，因而不能用来证明真实任务效果。

## 7. 最后一次审查发现了什么

独立审查检查了代码、配置、构建与部署脚本以及公开文档。发现一个需要修正的问题：构建脚本在共存导入探针完成前，就替换当前生效的后端清单。

为什么这是问题？假设原来有一个可用后端，新编译的候选因为 ABI 或依赖问题无法和 Receive 扩展同时导入。构建命令虽然报错，当前清单却已经指向这个失败候选，原来的可用版本被覆盖了。

修复后的步骤是：

```text
编译到独立目录
→ 本地回环传输测试
→ 写候选清单
→ 对候选执行导入与能力校验
→ 校验通过后才原子替换生效清单
```

测试分别覆盖：第一次构建失败时没有生效清单；已有版本时失败保持旧清单逐字节不变；成功探针执行期间旧清单仍有效，探针成功后才切换。探针本身不连接机器人。

另一个在产物检查中发现的问题是：发布筛选器把 SDK 原始发行包里的五个 egg-info 元数据文件也当成可丢弃缓存。可是这些文件已被来源清单锁定，上传时少了它们，服务器的完整性检查就会失败。现在只排除本项目生成的 egg-info，第三方锁定文件完整保留，并增加“全部 708 个锁定文件必须被部署选中”的测试。

这两个例子说明，重构需要检查运行之外的交付过程。模块调用正确，但安装或文件交付不完整，别人仍然无法复现。

## 8. 公共仓库的三种资料怎样分工

公开 README 和 guide 面向没有参与这次对话的人，需要解释项目做什么、支持哪些配置、怎样操作、输出是什么、哪些结果已经验证。它们不保留个人学习过程。

英文 technical_report 面向技术报告或文章读者，说明系统方法、几何与时间契约、受限控制、实验设置、量化结果与局限。不能把仿真的 0.748 分数写成 UR7e 实机成绩，也不能把一个 run 中的三条目标当作三次独立任务成功。

当前学习教材可以详细解释“字典是什么”“为什么要转张量”“为什么三维末端运动涉及六个关节”等基础困惑。学习资料越详细，不意味着项目 README 也应该变成教材。

以后公开发表还需要项目维护者确定新增代码许可、作者与论文元信息，并按研究要求完成实机复验和任务实验。文档没有替任何人虚构 DOI、作者、创新点或任务成功率。

## 练习与答案

**问题一：533 组比较全通过，能说新版任务成功率是 100% 吗？**

不能。这些是数值案例，不是机器人任务实验。任务成功率需要独立定义任务、初始条件、成功判据和多次真实试验。

**问题二：源码有一个新文件名，所以算法一定改了吗？**

不能这样判断。文件移动可以只改变组织方式。要看函数实现、数据处理、模型结构、参数、采样和控制逻辑是否发生变化。本次保留原算法和核心数值实现。

**问题三：如果原子替换清单之前探针失败，正确结果是什么？**

原来有可用清单就继续保留它；第一次构建没有清单就仍然没有。失败候选留在私有目录供诊断，不能冒充已验收的生效版本。

**问题四：新代码的安装包构建成功，为什么还不能直接控制机械臂？**

wheel 主要包含适配包，不包括全部模型、系统 ROS、目标机器编译的 RTDE 后端和现场设备配置。安装、文件验证、真实采集、推理与控制验收是不同层次。

**问题五：以后写技术报告时，哪个句子更准确？**

“旧版完成一次三目标受限链路短测；新版通过本机离线回归和模拟边界集成，尚待实机复验。”这比没有版本和条件的“完整复现成功”更有可核验性。
