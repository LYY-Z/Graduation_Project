## 1. 当前使用的硬件究竟贡献什么

“接口”是两部分约定怎样交付信息的边界。例如相机驱动提供 ROS 图像消息，RTDE 提供控制柜状态，模型接收固定名字和形状的数组。设备型号相同并不自动保证接口相同；还要明确数据格式、字段和单位。

| 来源 | 本项目实际使用的信息 | 在后续中的作用 |
|---|---|---|
| Gemini 335L 腕部相机 | 一路 RGB 彩色图 | 两帧图像成为网络视觉条件 |
| ROS 图像话题 | `/wrist_camera/color/image_raw` | 桥接进程从这里接收消息 |
| 光学 frame | `wrist_camera_color_optical_frame` | 校验消息确实来自预期图像坐标系 |
| UR7e RTDE Receive | TCP 位姿、六关节角、模式、控制柜时间 | 构造位置输入并保留状态证据 |
| 执行监控 Receive | 进一步读取 TCP 速度、力/力矩 | 检查静止、运动边界与到位 |
| 夹爪 | 当前保持原状态，无开合指令 | 不进入本 checkpoint 的动作输出 |

这里的 RGB 是红、绿、蓝三个颜色通道；没有把深度、点云、第二只相机或夹爪传感器输入网络。光学 frame 的名称是一个数据标签，它不包含自动求好的相机到机械臂变换。

机器人 IP 在文档中写成 `192.0.2.1`。它只用于说明配置形式，实际运行时由操作者在本地配置填入真实地址，不应在学习笔记中传播机器或账户信息。

## 2. 先走一遍从消息到数组的路线

```text
相机驱动给出 ROS Image
  ├─ 像素字节：data
  ├─ 几何格式：height、width、step、encoding
  └─ 来源与时间：header.frame_id、header.stamp
      ↓ 解码并检查
原图数组 (480,640,3)，uint8，RGB
      ↓ 中心正方形裁剪
裁剪数组 (480,480,3)
      ↓ 面积插值缩放
桥接帧数组 (96,96,3)，uint8，RGB
      ↓ 原子 NPZ 交换；推理侧读取并保存历史
每帧转成 (3,96,96)，float32，并除以 255
      ↓ 两帧堆叠，再增加一个批次轴
网络输入 image (1,2,3,96,96)
```

同一时期，机械臂状态走另一条路线：

```text
UR 控制柜状态 → 只读 Receive → RobotSample 历史
  ↓ 选每帧之前最近的一份状态
每帧的报告 TCP 三维位置 p，单位米
  ↓ 相对会话起点做工程映射
每帧的二维 agent_pos，仿真动作坐标尺度
  ↓ 两帧堆叠，再增加批次轴
网络输入 agent_pos (1,2,2)
```

这两条路线在观察构造时按时间汇合。模型没有自己连相机或读控制柜，也不会从图片文件名猜机器人位置。

## 3. 一张 RGB 图片为什么有三个轴

数组 `(480,640,3)` 中，第一轴是高度 H，第二轴是宽度 W，第三轴是颜色通道 C。第一项不是宽度；OpenCV 的某些函数参数却采用 `(宽,高)`，所以代码会显式把 `size_hw` 拆成 `out_h, out_w`，再按函数要求传入。

“像素”是图片上的一个位置；RGB 像素包含三个通道值。例如：

```python
rgb[10, 20] = [255, 128, 0]
```

它表示第 10 行、第 20 列的颜色，不是机器人坐标 `[255,128,0]`。`uint8` 指每个通道使用 8 位无符号整数，可表示 0 到 255。全黑 `[0,0,0]`、全白 `[255,255,255]`；颜色解释还要遵守 RGB 次序。

ROS 消息的编码可能写 `rgb8` 或 `bgr8`。后者通道次序是蓝、绿、红。`image[..., ::-1]` 把最后一轴倒过来，从 BGR 变成 RGB；省略号 `...` 表示保留其他所有轴。这不是左右翻转照片，也不是改变相机朝向。

### `step` 为什么不能忽略

`step` 是一整行占多少字节，可能比 `width×3` 更大，因为有些数据格式在行末填充。假设宽度为 2，一行有效 RGB 有 6 字节，但 `step=8`，每行还有 2 字节填充。两行消息长度为 16 字节，不是 12。解码先按行读完整 8 字节，再切出每行前 6 字节，才能还原正确图片。

本工程拒绝不支持的编码、无效尺寸和长度不匹配的字节缓冲区。数据“能被 reshape 成某个数组”不代表解码正确，先检查消息声明才有意义。

## 4. 中心裁剪和缩放具体删掉了什么

480 高、640 宽的原图，中心正方形边长取较小值 480。横向起点为 `(640-480)//2=80`，纵向起点为 0；切片为：

```python
crop = rgb[0:480, 80:560]
```

Python 切片右端不包含在内，所以取列 80 到 559，总共 480 列。左右各去掉 80 列。`//` 是整除，用于得到整数索引。

缩放将这张 480×480 图压到 96×96，宽高各缩小 5 倍。使用 `cv2.INTER_AREA` 面积插值会综合原图区域的像素，而不是简单把每五个像素只拿一个。因此一个最终像素可包含一个小区域的平均视觉信息。

ROI 是 region of interest，即明确指定感兴趣区域，形式是 `[x,y,width,height]`。当前默认无显式 ROI，执行中心裁剪。把 ROI 改成更贴近任务的区域是一个新的输入设计决定，需要检查可见范围和训练分布，不能仅因为模型尺寸对了就认定无影响。

**形状通过并不能证明目标可见。** 如果物体位于原图最左边 50 列，中心裁剪已经把它删掉，后面再强的视觉编码器也无法恢复当前视野里不存在的信息。

## 5. 从 HWC 到 CHW，不是旋转图片

外部预处理的核心片段是：

```python
rgb.transpose(2, 0, 1)
np.ascontiguousarray(..., dtype=np.float32) / 255.0
```

原来轴顺序是高、宽、通道，`transpose(2,0,1)` 把旧第三轴放到前面，得到通道、高、宽。空间中的同一个像素仍在相同位置，只是存取方式从 `rgb[y,x,c]` 变为 `image[c,y,x]`。`ascontiguousarray` 确保内存排列便于后续库使用；`float32` 是常见神经网络浮点类型。

`128/255≈0.50196`，`255/255=1`，`0/255=0`。这一步只处理像素值的基本尺度，策略内部仍有原 checkpoint 的 normalizer，下一章会区分两层处理。不要看到已经除以 255，就手动删掉模型 normalizer。

## 6. 为什么用一个 NPZ 文件隔开两个 Python

ROS Humble 的系统 Python 3.10 和原策略依赖的隔离 Python 3.9 各有自己的依赖约束。桥接用前者订阅 ROS，模型用后者加载 PyTorch 等库。NPZ 是 NumPy 保存一组命名数组的文件格式，两边都能读取，不必互相导入对方全部依赖。

[camera.py](../../../03_code/diffusion_policy_ur7e/src/dp_ur7e/hardware/camera.py) 中的 `CameraFrame` 将像素与元数据放在同一个帧对象中，`FrameStore` 负责读写。文件中不仅有 `rgb`，还有序号、流 ID、主机时间、ROS 时间、来源 frame、原图尺寸和编码、回调前图像年龄等。

这里保存的是**最新一帧的交换文件** `.runtime/wrist_rgb.npz`。写新帧会替换旧帧，它不等于所有历史帧的录像。推理侧采集线程持续读取新序号，把需要的历史留在内存；长期证据另由 `RunWriter` 保存。

### “原子替换”解决什么问题

如果直接打开正式文件写入，另一进程可能在写到一半时读取，看到不完整的 NPZ 容器或部分元数据。当前顺序是：

1. 为本次帧创建唯一的临时文件。
2. 把数组和元数据完整写入，刷新用户态缓冲并请求文件同步。
3. 使用 `os.replace` 将临时文件替换正式路径。
4. 无论成功失败，清理本次遗留临时文件。

对于同一文件系统上的这个替换操作，读取方看到旧的完整版本或新的完整版本。它不保证帧永远新鲜，所以还要检查时间、`stream_id` 和 `sequence`。

`sequence` 是单次桥接运行内递增的帧序号；`stream_id` 是这次桥接启动的身份。序号 20 后再次读到 20，应跳过；桥接重启后出现新流的序号 0，不能当作原流连续帧。观察历史已经投入使用后，桥接重启会要求重启对应会话，防止把不连续来源混合成一个历史窗口。

## 7. 六轴机械臂的“六个数”有两种完全不同的意思

关节空间用六个关节角描述机械臂：

```text
q_rad = [q1, q2, q3, q4, q5, q6]，每项单位 rad
```

TCP 空间用位置和姿态描述工具中心：

```text
actual_tcp_pose = [x, y, z, rx, ry, rz]
                  └─ 米 ─┘  └─ 旋转向量，弧度 ─┘
```

TCP 是 tool center point，即工具中心点，是控制器用来表示末端运动的参考点。基坐标系 UR base 固定在机器人底座附近，工具坐标系随末端转动。相同的六维数组长度不意味着同一个空间。

旋转向量的方向表示旋转轴，长度表示旋转角。例如 `[0,0,1.5708]` 表示绕对应 Z 轴转约 90°，一般不能把 `rx,ry,rz` 当成依次绕 X、Y、Z 的三个欧拉角。计算姿态差时，代码转换为旋转矩阵再比较，而不是简单把这三项逐项减完相加。

### 244 mm 的工具偏移为什么不能再加一次

报告指定法兰到 TCP 的偏移为 `[0,0,0.244,0,0,0]`，前半单位米、后半单位弧度。它描述“TCP 相对法兰在哪里”，不描述“TCP 相对机器人底座在哪里”。

控制器返回的 `actual_TCP_pose` 已经包含当前激活工具的偏移。若当前激活的就是报告这个 TCP，直接读回的平移部分就是需要的位置；再加 0.244 m 会重复计算。工具法兰 Z 轴还可能朝其他方向，更不能假定总是给 base Z 增加长度。

通用变换写成：

$$T_{BR}=T_{BC}T_{FC}^{-1}T_{FR}.$$

`T` 是包含旋转和平移的 4×4 变换矩阵；B 是 base，F 是法兰，C 是当前激活 TCP，R 是报告 TCP。先从当前 TCP 回到法兰，再走到报告 TCP。如果两套偏移相同，中间两个矩阵相消，结果等于原读回位置。此处的数学转换不等于程序已自动确认现场激活 TCP；实际执行前还会读控制端偏移核对，而且不会调用 `setTcp()` 自动改设置。

## 8. 状态读取为什么前后看两次 timestamp

Receive 接口在后台更新缓存，多个 getter 各读一个字段。如果刚读完 TCP，新包到达，然后再读关节角，就可能把不同控制周期的字段拼在一起。

代码先读一次控制柜 timestamp，读取全部字段后再读一次；相同才接受这个快照。若变化则重试，连续几次都变化便报错。它减少混合包问题，不是创建更精确的硬件同步，也不能把本地读取时刻当成编码器真实采样时刻。

只读状态连接负责观察历史；执行监控可另有一个字段更多的只读连接；私有 Control 是发送边界。这些连接职责不同，不等于多个程序同时控制机器人。

## 9. `agent_pos` 是怎样从 TCP 位置得到的

checkpoint 在仿真 Push-T 上训练，低维状态是二维推具位置。新机械臂有六个关节，并不能把模型输入直接改成六个关节角，因为权重与输入维度早已约定。

当前用“相对锚点工程映射”：会话开始读取 TCP 三维位置为 `p0`，把它定义成模型坐标 `[256,256]`。沿 base X、Y 每移动 0.001 m，模型对应一维增加 1。

$$u=u_0+\operatorname{diag}(s)E(p-p_0),$$

其中 `u0=[256,256]`，`s=[1000,1000]` px/m，`E=[[1,0,0],[0,1,0]]`，`p` 和 `p0` 单位米。E 从三维位移中取 X、Y；两个轴要求单位长度且相互正交。

例如起点 `p0=[0.250,0.420,0.700] m`，当前 `p=[0.252,0.419,0.700] m`：

```text
p-p0       = [0.002, -0.001, 0] m
取 X/Y     = [0.002, -0.001] m
乘 1000    = [2, -1]
加 [256,256] = [258,255]
```

逆映射也能手算：模型动作 `[259,254]` 对应相对起点 `[3,-2] mm`，候选 base 位置 `[0.253,0.418,0.700] m`。这只是尚未限幅的候选位置，不能直接发送。

### “px”不是相机上的一个真实像素

真实图像输入是 96×96，模型状态和动作范围仍可用 0–512 这一仿真尺度。两者属于不同量：前者是图像网格大小，后者是原任务状态与动作坐标。这里没有使用相机内参、手眼外参或桌面平面求解，`[258,255]` 也不是把图片第 258 列投影到机械臂。

映射可逆只说明数字上能来回转换，不说明视觉方向、真实桌面方向和仿真任务语义已对应。模型看到腕部图，状态用 base XY 工程位移，是否产生有意义的真实任务动作仍需独立研究。越界输入被拒绝，不能把坐标静默夹进范围而掩盖错误。

## 10. 三种时间不能直接相减

时间戳需要知道“从什么起点计数”。两只表即使单位都叫秒，也可能没有共同零点。

| 时间 | 零点或来源 | 当前负责的问题 |
|---|---|---|
| ROS header stamp | ROS 时钟域；随驱动消息提供 | 图片进入桥接回调前已经延迟多久 |
| 控制柜 timestamp | 控制器运行时间 | 状态包是否推进、控制柜是否重置 |
| 服务器 monotonic | 同台主机的单调时钟 | 图像与状态在本机接收/读取上的因果顺序和年龄 |

单调时钟不会因为人为调整日历时间而向后跳，适合算间隔。UTC 适合记录“2026 年某日发生”，不适合直接替代所有新鲜度判断。不要拿控制柜 uptime 12345 s 减去一个 Unix 时间戳来算延迟。

桥接和推理进程必须在同一主机的 monotonic 时钟域中使用本帧交换方案。简单把 NPZ 复制到另一台电脑，数值看起来完整，也不能假定其 monotonic 时间仍可直接比较。

“因果配对”表示不拿图像之后才读取的未来状态来解释过去图像。它依据本机接收时间，而不是硬件曝光触发；网络延迟和读取延迟没有因此消失。

## 11. 两帧窗口一步步怎样选

历史包含多个相机帧和机器人状态。“窗口”是本轮模型需要的一小段历史。本 checkpoint 需要两帧，名义间隔 0.1 s，最大选择偏差 0.05 s，构造时最大有效年龄 0.5 s。

假设最新图像本机时间为 10.200 s，本轮 `now=10.230 s`，相机历史有 10.067、10.100、10.133、10.167、10.200。两个目标时刻为 10.100 与 10.200。

1. 对目标 10.100，找不晚于它的最近图像，得到 10.100。
2. 对目标 10.200，找不晚于它的最近图像，得到 10.200。
3. 每帧分别找不晚于该图像的最近状态，例如 10.096 与 10.192。
4. 图像与状态相差 0.004、0.008 s，均小于 0.05 s。
5. 最旧状态到 now 为 0.134 s，小于 0.5 s；两帧序号不同，因此可以形成窗口。

如果第一目标只能找到 10.040 的图像，偏差 0.060 s，就拒绝；如果没有 10.100 前的状态，也拒绝，不能用 10.105 的状态补过去。两帧实际间隔可以不是精确 0.100 s：按不晚于目标的规则选到较早样本时，只要各项误差均在范围内就可能通过。应查看记录中的实际时刻，而不是把名义频率当作测量结果。

`deque` 是可在两端快速追加/移出的队列；历史设置最大长度，避免永远积累耗尽内存。重复序号和重复控制柜 timestamp 不作为新样本；时钟倒退、运行中桥接流改变等情况有明确的异常处理。

### 0.05 s、0.5 s、1.5 s 为什么不是同一个限制

`0.05 s` 限制选样偏差或图像与其配对状态的本机时差。`0.5 s` 检查构造观察时输入是否太旧，包含图像在 ROS 回调之前已发生的延迟。`1.5 s` 是推理之后到实际发送时，对最旧有效输入的额外上限。

例如一张图在桥接接收时已经延迟 0.10 s，本机再经过 0.15 s 才构造，图像有效年龄约 0.25 s；推理又花 0.60 s，控制检查与记录再花 0.10 s，发送时约 0.95 s。不能把年龄从“推理结束”重新归零，也不能仅检查两帧里最新的一帧。

## 12. 最终的方括号逐轴读懂

```python
observation = {
    "image": image_array,       # [1,2,3,96,96]
    "agent_pos": position_array,  # [1,2,2]
}
```

形状写在方括号里只是说明每轴长度，不是数组真实内容。`[1,2,3,96,96]` 不表示只输入这五个数字。

| 轴 | image 的长度与含义 | agent_pos 的长度与含义 |
|---|---|---|
| 第 0 轴 B | 1 个批次样本，即一个观察窗口 | 同一个窗口 |
| 第 1 轴 T | 2 个历史时刻，旧帧在前 | 同两帧各自配对的位置 |
| 第 2 轴 | 3 个颜色通道 R/G/B | 2 个二维位置分量 |
| 第 3、4 轴 | 96 行、96 列 | 不存在 |

`image[0,1]` 取新图，剩余形状 `(3,96,96)`。`image[0,1,2,10,20]` 是新图第 10 行第 20 列的蓝通道浮点值。`agent_pos[0,0]` 是旧图配对位置，可能 `[256.0,256.0]`；`agent_pos[0,1,0]` 只取新位置的第一维。

```python
np.stack([image_tensor(f.rgb) for f in selected_frames])[None]
```

`stack` 把两张 `(3,96,96)` 沿新轴堆为 `(2,3,96,96)`；`[None]` 再添加长度为 1 的批次轴。不是把两张图片相加，不是通道变成 6，也不是复制一帧凑两帧。

`evidence` 是同时返回的证据字典，包含时间、序号、原 TCP、关节角和模式等。网络只使用约定的 `image` 和 `agent_pos`；记录六关节不等于网络把六关节当输入。

## 常见问题

**为什么只有两帧，不能随手改成五帧？** 网络条件形状与 checkpoint 训练配置一致。更多历史不是无成本增强，必须同时有匹配模型结构与权重依据。

**相机 30 fps，策略就是 30 Hz 吗？** 不是。驱动采集、桥接发布、帧文件轮询、观察构造、推理、实际运动都有各自速度。整个控制周期还包含等待运动结束。

**有 camera optical frame 和 TCP，不就能投影了吗？** 还缺相机内参、坐标变换和任务平面等实际标定。本工程没有把这些自动补出来。

**同一张图片读两次不就是两帧吗？** 不是。序号和来源时刻相同就是重复读取，不能提供时间变化。代码会拒绝用同一帧凑窗口。

**输入已新鲜，预测为何还会过期？** 推理、控制查询和写记录都消耗时间，所以发送前必须再次从原始来源算年龄。

## 练习与答案

1. 对 480×640 图像执行默认中心裁剪，横向取哪一段？一个值为 128 的通道转成网络输入后大约是多少？
2. `p0=[0.30,0.20,0.60] m`，当前 `p=[0.3015,0.1995,0.60] m`，`agent_pos` 是多少？
3. 目标时刻 20.000 s，候选图为 19.960、20.005 s，应选哪张？如果最新的因果状态为 19.900 s，能通过吗？
4. 图像在 30.000 s 接收，回调前年龄 0.12 s，发送发生于 31.000 s，这张图的有效年龄是多少？
5. 当前激活 TCP 偏移与报告都为 244 mm，返回 z=0.700 m，报告 TCP 的 z 应直接变成 0.944 m 吗？

答案：

1. 取列 `[80:560]`、行 `[0:480]`；通道值约为 0.50196。
2. 相对位移 `[1.5,-0.5] mm`，得到 `[257.5,255.5]`。
3. 选 19.960，不能用未来图 20.005。它与状态相差 0.060 s，超过 0.05 s，因此拒绝。
4. 约 1.12 s；还要与其他图像及状态比较，整窗使用最旧有效来源。
5. 不应该。当前读回已经包含激活 TCP，两个偏移一致时报告位置保持原值；额外加长是重复补偿。
