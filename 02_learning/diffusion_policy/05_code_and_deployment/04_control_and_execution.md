# 04　二维预测怎样成为一条可核验的小运动

[教材目录](README.md) · 上一章：[模型和推理](03_model_and_inference.md) · 下一章：[阅读和操作](05_reading_and_operation.md)

本章沿着一条候选从生成到结束的过程阅读。先解释纯数字变换，再解释控制器检查、发送和实际反馈。对应 [pipeline.py](../../../03_code/diffusion_policy_ur7e/src/dp_ur7e/pipeline.py)、[control/safety.py](../../../03_code/diffusion_policy_ur7e/src/dp_ur7e/control/safety.py)、[control/robot.py](../../../03_code/diffusion_policy_ur7e/src/dp_ur7e/control/robot.py)。本章说明代码，不授权立即运行设备；后文的执行命令也只是有条件的操作模板。

## 1. 把“模型认为去哪里”与“这次允许走多少”分开

模型返回的是仿真动作尺度中的二维目标 `u*`。工程映射把它变成 UR base 中的候选位置 `p*`。候选可能距离当前几十毫米，而本阶段只允许毫米级小运动，因此执行层不会直接把 `p*` 当作 `moveL` 目标。

完整路线如下：

```text
action[0,0]：二维仿真目标
  ↓ 检查形状、有限性和仿真边界
mapping.to_base：三维候选位置，米
  ↓ desired_xy - actual_xy
原始二维位移向量
  ↓ 向量范数限幅
最多 1 mm 的方向向量
  ↓ 平滑，历史初值为零
较温和的本轮增量
  ↓ 剩余路径预算限幅
  ↓ 加到当前 X/Y，Z 和旋转固定为初始值
六维 TCP 目标
  ↓ 完整目标检查、控制查询、最新状态与原始来源年龄
私有控制接口 moveL
  ↓ 实际 TCP/q/速度/力反馈及异步状态
连续到位确认 → 下一轮重新观察
```

“限幅”是限制一个数值或向量的最大允许大小；“平滑”是把当前提议与过去增量组合，减少突变。它们不能赋予候选正确任务语义，只限制当前阶段允许发生的运动。

## 2. 运动限制对象先读哪几个字段

`MotionLimits` 用 dataclass 集中保存限制。普通构造默认值更保守，实际预演/执行流程明确使用 `MotionLimits.visible()`。因此阅读时要看调用端到底创建了哪个对象，不能只看类定义的第一组默认值。

| 字段／含义 | `MotionLimits()` 普通默认值 | 实际流程选择的 `MotionLimits.visible()` |
|---|---:|---:|
| `max_step_m`，单条目标距离 | 0.0002 m，即 0.2 mm | 0.001 m，即 1 mm |
| `max_path_m`，累计命令路径 | 0.0006 m，即 0.6 mm | 0.003 m，即 3 mm |
| `radius_m`，距初始 TCP 的包络半径 | 0.002 m，即 2 mm | 0.003 m，即 3 mm |
| `speed_m_s`，命令平移速度 | 0.001 m/s，即 1 mm/s | 0.002 m/s，即 2 mm/s |
| `acceleration_m_s2`，命令加速度 | 0.005 m/s² | 同为 0.005 m/s²，即 5 mm/s² |
| `smoothing_gain`，当前方向权重 | 0.2 | 0.5，当前与历史各一半 |
| `max_commands`，最多命令条数 | 3 | 同为每次运行最多 3 条 |
| `max_source_age_s` | 1.5 s | 同为原观察到发送最多 1.5 s |
| `move_timeout_s` | 3 s | 同为单条运动等待到位最多 3 s |

左列更严格的默认值仍用于普通对象构造和相关测试；运行入口显式选择右列，后面的手算全部按右列。平滑系数 0.5 没有秒单位，不要把它读成 0.5 s 的来源年龄。

小于 0.00001 m，即 0.01 mm 的候选增量会作为保持处理。Z 和姿态锁定在本次初始值，夹爪不发送开合命令。

限制构造还有正值、有限数和硬上限校验。随便在 YAML 增加 `max_step: 10` 不会自动改变这里的值；直接修改硬上限也不是日常“调参”。这套教材按当前已保留的限制解释，不建议用放宽限制解决时序、IK 或控制错误。

### 三种距离预算各限制什么

单步限制约束本条起点到目标的距离；累计路径是各条承诺命令距离的和；初始包络约束每个点离会话起点不能太远。

如果先向右 1 mm 再向左 1 mm，净位移约为零，累计路径却消耗 2 mm。如果连续向右三次，每次 1 mm，累计和最终半径都可能达到 3 mm。它们相互补充，不能只保留“最后没离起点很远”这一项。

预算按一次程序运行持有。重新启动会重新建立会话和锚点，不应通过无限重启把三条限制变成无人看护连续控制。

## 3. 手算一次范数限幅和平滑

设当前 TCP XY 为 `[0.250,0.420] m`，逆映射候选为 `[0.253,0.424] m`。原始位移为 `[0.003,0.004] m`，也就是 `[3,4] mm`。

欧氏范数为 `sqrt(3²+4²)=5 mm`。限制 L=1 mm，所以整个向量乘 `1/5`：

```text
原向量      [3.0,4.0] mm，长度 5.0 mm
限幅后      [0.6,0.8] mm，长度 1.0 mm
首次历史    [0.0,0.0] mm
平滑后      0.5*[0.6,0.8] + 0.5*[0,0]
          = [0.3,0.4] mm，长度 0.5 mm
候选新 XY   [0.2503,0.4204] m
```

如果错误地各轴截到 1 mm，会得到 `[1,1] mm`，长度为 1.414 mm，已经超过单步允许值。当前 `norm_clip` 保留方向并缩短总长度，避免这个对角线问题。

第二轮如果限幅方向仍为 `[0.6,0.8] mm`，上一条实际承诺的增量是 `[0.3,0.4] mm`，平滑得到 `[0.45,0.60] mm`，长度 0.75 mm。第三轮同方向可得到长度 0.875 mm。教学例子的累计为 2.125 mm，不会恰好三次都是 1 mm。

真实反馈存在细微差异，且发送前重新读取状态，最后的三维距离也可能包含固定高度与测量抖动，因此历史运行的 0.5004、0.7740、0.8446 mm 不应硬套为这个理想同方向数列。

### 用公式对应代码

$$C(v,L)=v\min\left(1,\frac{L}{\max(\|v\|,\varepsilon)}\right),$$

$$d=C(p^*_{xy}-p_{xy},L),\qquad
\bar d=g d+(1-g)d_{prev},$$

$$d_{final}=C\left(\bar d,\min(L,P-\ell)\right).$$

`g=0.5`，`P=0.003 m`，`ℓ` 是累计承诺路径。很小的 `ε` 避免零向量除零。最后一层限制不能省：平滑、剩余预算和实际发送状态各有约束，初步限幅通过不代表最终通过。

## 4. 为什么 Z 和旋转直接取初始值

模型只输出二维平面目标。它没有预测抬高、压低、转动工具或夹爪开合。目标组装为：

```python
target = initial_pose.copy()
target[:2] = actual_pose[:2] + step
```

`target[:2]` 是 X、Y，`target[2:]` 包括 z、rx、ry、rz，保留初始姿态。检查目标时要求这些项与初始值一致；检查实际反馈时则允许有限的小偏差，例如实际 Z 相差不超过 0.15 mm、旋转差不超过 0.002 rad。

“目标锁定”与“实测容差”不同：前者是命令内容必须固定，后者承认传感器与控制跟踪可能出现微小偏差，并规定超出后停止。它不证明这些阈值就是设备测量精度。

## 5. `propose`、`validate_target`、`commit` 各干什么

`ActionGuard` 保存初始姿态、上一条增量、最后目标、命令数和累计路径。

| 操作 | 它做什么 | 它不会证明什么 |
|---|---|---|
| `propose` | 根据候选、当前状态、来源年龄计算小目标 | 没有实际发送或到位 |
| `validate_target` | 对最终六维目标和当前状态重新检查距离、包络、锁定及预算 | 不建立网络，不求实际反馈 |
| `commit` | 通过再次检查后更新预算、历史增量和最后目标 | 承诺命令不等于控制器已确认或到位 |

原发送流程在调用 `moveL` 前承诺预算，避免失败后把可能已经开始的命令当作未发生并自动重试。若发送没有收到 ACK，物理上也可能存在不确定性；不能简单回滚预算然后再次发送旧目标。

预演流程只计算候选，不假装机器人已到达每个候选，因此它不会完整模拟真实运动后的历史状态。预演适合检查数据、候选和限制，不是可以直接回放的运动计划。

## 6. 二维目标如何让六个关节工作

控制器接收的是六维 TCP 目标，随后协调六个关节实现笛卡尔空间运动。`moveL` 表示沿笛卡尔直线运动的控制接口；它不同于直接给六个关节目标的 `moveJ`。

IK 是 inverse kinematics，即逆运动学：给定希望的 TCP 位姿，求一组关节角。一个位姿可能有多个解，因此代码用当前关节角作近邻参考，并限制目标解相对当前每轴变化不超过 0.01 rad、相对初始每轴不超过 1°。这样可以拒绝突然跳到另一关节解分支的候选。

这不意味着上层学习了六自由度动作。网络只输出两维，Z、旋转被执行层固定；六轴机构为了实现这两维小平移，仍需要各轴协调，而且每轴变化大小可以不同。

控制器还检查目标位姿和目标关节是否在其安全限制内。它与完整环境碰撞规划不同：TCP 在小范围内不自动证明机械臂全部连杆、腕部相机、工具、夹爪和线缆都不会碰到环境。本次没有调用 cuRobo 规划路线。

## 7. 真正创建 Control 前，主流程做了什么

按 [pipeline.py](../../../03_code/diffusion_policy_ur7e/src/dp_ur7e/pipeline.py) 的实际调用顺序，执行模式会核对显式选项、TCP 声明和支持的映射轴；创建运行记录和互斥锁；加载模型；建立传感器会话；执行一次预热并丢弃输出；读取静止基线；检查 Dashboard，之后才可能创建私有控制对象。

`--site-ready` 是操作者对现场看护、空间、急停和 TCP 的显式声明，不是机器视觉自动检查现场。配置中的 `active_tcp_offset_verified_on_pendant: true` 也应来自真实人工核对，不应通过一段脚本自动写 true 来代替核对。

Dashboard 是控制柜提供的状态查询接口。当前用只读请求确认：机器人处于运行模式、安全状态正常、没有其他程序正在运行、处于远程控制。代码不会自动 power on、play、解除保护停止或改变模式。

互斥锁避免本工程同时启动两份受限执行器。它不能发现世界上所有外部控制程序，所以仍需现场和进程范围的实际检查。

## 8. 每条命令下发前为什么又检查很多遍

预测时的状态到了发送时已经过去一段时间，期间机器人可能被其他控制源移动，控制查询也可能耗时。执行器不会默认“刚刚通过，所以永远有效”。

每条目标的主要顺序为：

1. 读反馈并检查新鲜度、模式、静止和运动包络。
2. 重新验证目标距离及预算。
3. 读激活 TCP，要求与 `[0,0,0.244,0,0,0]` 一致。
4. 做位姿安全检查、近邻 IK、关节变化和关节安全检查。
5. 确认此前没有尚未完成的异步运动。
6. 读取私有控制脚本缓存 ready，要求连续稳定约 20 ms，总等待不超过 300 ms。
7. 再读最新状态，检查静止、目标和最旧来源年龄。
8. 把发送意图写入事件日志。
9. 因写盘也会耗时，再读一次状态和来源年龄，合格后承诺预算并发送。

这不是为了堆砌重复代码，而是每一个可能耗时或改变条件的边界后都确认“现在仍然满足”。特别是第 8 步磁盘若突然很慢，旧观察不能因日志已记录而获得继续执行的权利。

### 常见反馈阈值怎样读

| 检查 | 当前规则 |
|---|---|
| 本机反馈年龄 | 0 到 0.1 s 内 |
| 控制柜时间 | 不能倒退；不推进超过约 0.15 s 会拒绝 |
| 模式数值 | safety mode=1、robot mode=7 |
| 初始包络 | TCP 平移距初始不超过 3 mm |
| 实际高度与旋转 | Z 偏差 ≤0.15 mm；旋转差 ≤0.002 rad |
| 实际关节累计变化 | 每轴相对初始 ≤1° |
| 实际平移速度 | visible 条件下监控上限为 3 mm/s |
| 实际角速度 | 范数 ≤0.01 rad/s |
| 力和力矩 | 力范数 ≤50 N；相对基线力变化 ≤5 N；力矩变化 ≤0.5 N·m |
| 目标线段跟踪 | TCP 到本条起止线段距离 ≤0.15 mm |

命令速度 2 mm/s 与监控上限 3 mm/s 并不矛盾：前者是给控制器的参数，后者是反馈异常判断阈值。二者都不是你应在现场随手放大的设置。

## 9. 为什么使用私有控制 SDK

SDK 是供程序调用设备功能的软件库。原 `ur_rtde` 的部分异常路径可能自动重连、重新上传控制程序或重发命令。本阶段希望通信异常后停止在明确失败状态，避免旧目标在上层新鲜度检查之外恢复。

所以当前保留系统安装的原库用于 Receive，只把发送边界指向项目私有控制扩展。源码在 [third_party/ur_rtde_guarded/source](../../../03_code/diffusion_policy_ur7e/third_party/ur_rtde_guarded/source)，本机编译扩展与清单在 `.runtime/control_backend/`，清单为 `manifest.json`。

加载器校验私有路径、二进制哈希、相应源码哈希和必须暴露的能力标记，包括不自动重连、立即受控下发和只读 ready 查询；不满足就拒绝。它不会悄悄退回普通 `rtde_control` 来“让程序先跑起来”。这就是 fail closed：检查失败时不开放发送路径。

私有修改还为运行中的命令和发送设置有限等待，并让停止未获确认时明确报错。但它不是安全认证，也不能让普通 Linux 调度成为硬实时。初始化握手仍有上游机制，网络断开后的真实停止也不能仅凭 Python 日志宣称已确认。

## 10. ACK 为什么还不能算“运动完成”

ACK 是 acknowledgement，即命令确认。`moveL` 返回确认说明控制调用获得了相应响应，不直接告诉你 TCP 到了哪里。实际位置必须从 Receive 反馈读取。

```text
filtered_prediction：预测与过滤后的候选
  ↓
motion_dispatch_intent：准备发送，意图已记录
  ↓ 最终检查
motion_command_acknowledged：控制调用获得确认
  ↓
motion_feedback：实际位姿、关节、速度、力、异步进度
  ↓ 位置近 + 速度低 + 异步完成状态改变，连续三次
motion completed=true：本条目标按当前规则到位
```

到位不是“等一秒就当成功”。当前同时看三类证据：

1. 异步进度为完成状态，且和开始前的完成状态不同，说明不是误读上次残留结果。
2. 实测位置距目标在容差内。
3. 平移速度足够低，连续三次满足上述条件。

位置容差取 `min(0.05 mm, 0.4×本条目标距离)`。例如目标只有 0.01 mm，容差不能仍放到 0.05 mm，否则完全没动也可能被当成到位。0.5 mm 目标的容差为 0.05 mm；0.02 mm 目标的容差为 0.008 mm。

记录 `motion_count` 一般统计完成条数。如果首条开始移动但随后超时，完成数可能仍为零；因此“完成零条”不能单独证明没有任何物理位移。应合看 intent、ACK、feedback、失败和停止记录。

### 反馈为什么先放内存再落盘

正在运动时如果每次反馈都同步写慢磁盘，监控可能被文件系统阻塞。当前把这一条运动的反馈先缓存在内存，到位或停止后再写事件；发送意图则在发送前落盘，并在写盘后再检查新鲜度。

这样能减少磁盘挡住监控的问题，但也意味着异常退出或进程被强杀时可能没有全部内存反馈落盘。不能把缺少反馈自动解释为没有运动，也不应声称事件记录解决了所有持久化风险。

## 11. 一条失败如何退出，以及清理只管什么

`GuardedRobot.move` 出现运行异常时尝试 `stopL`；若停止也失败，会写 `stop_failed` 并保留原错误。关闭时尝试停止运动、停止自己上传的控制脚本、断开自己的控制连接；传感器会话再退出采集线程和 Receive。

程序不会自动回原点、重发旧命令、解除保护停止、恢复运行或杀死所有名字像 Python/ROS 的进程。清理范围是本进程确实持有和创建的资源。独立终端启动的相机驱动和桥接应在正常完成后由操作者分别退出，不能依赖推理进程猜测谁拥有它们。

Ctrl+C 通常触发 Python 中断和清理，SIGTERM 也有相应处理；断电、强杀和网络丢失并不保证清理执行。运动异常优先按现场预案使用物理急停。软件尝试停止与物理停止得到确认仍是不同事实。

## 12. 怎样正确阅读旧实机的三个数字

原版一次短测命令距离约 0.5004、0.7740、0.8446 mm；对应实测起止位移约 0.4950、0.7510、0.8314 mm。三条目标有反馈支持，并在当前到位规则下完成。

累计命令距离约为 2.1190 mm，是各条目标距离之和；净实测位移约为 2.0223 mm，是第一次前位置到最后一次后位置的直线距离。沿 132 个反馈点逐段累加得到的量又是另一种统计，容易受采样和噪声影响。

这些数字不能支持“任务准确率”“碰撞安全认证”“六自由度学习控制”或“新版已经实机复验”。它们支持的是原版当时那次受限数据到运动链路的事实。

## 常见问题

**看到机械臂只有某几轴明显变化，是不是没用六轴？** 不是。小范围笛卡尔平移可以让不同关节变化不同，部分变化小到肉眼不明显。

**只要 `moveL=True` 就行吗？** 不行，还需要反馈到位、速度和异步状态，也要确认任务是否达成；三层结论逐级增加证据。

**为什么不收到 ACK 后自动重试一次？** 因为不能排除命令已开始而响应丢失。旧目标重发还会绕过新输入和运动预算，不符合当前失败退出设计。

**所有检查通过是否保证没有碰撞？** 不能。这些是当前工程边界检查，现场空间、工具和线缆仍需实际核验，也没有完整环境碰撞规划。

**预演能通过，执行为什么可能失败？** 预演没有控制连接，不执行私有后端、ready、真实下发和运动反馈路径。它减少上游不确定性，不覆盖下游全部条件。

## 练习与答案

1. 原始位移 `[6,8] mm`，最大范数 1 mm，第一次平滑系数 0.5，最终平面增量是多少？
2. 已消耗累计路径 2.8 mm，还剩多少？若平滑增量长度 0.6 mm，最后最多保留多少？
3. 完成两条各 1 mm、方向相反的运动，净位移近零，累计路径是否也近零？
4. 0.02 mm 目标的到位容差按当前公式是多少？为什么不一直用 0.05 mm？
5. 事件中有 `filtered_prediction executed=false` 和后面的 `motion completed=true`，怎样解释？
6. 首条 `moveL` 未获确认、最终完成数为零，可以写“机器人完全没动”吗？

答案：

1. 原长度 10 mm，先变为 `[0.6,0.8] mm`，首次再变为 `[0.3,0.4] mm`，长度 0.5 mm。
2. 剩 0.2 mm，最终范数最多 0.2 mm，还要继续满足初始包络与完整三维目标检查。
3. 不会。累计路径约 2 mm；净位移是起终点差，预算消耗不是它。
4. `min(0.05,0.4×0.02)=0.008 mm`，避免容差大于目标而把未移动误判为到位。
5. 预测事件本身不证明执行，所以为 false；后续独立运动事件记录了真正执行并到位。应按整条事件链解释。
6. 不可以。没有确认可能产生不确定性，应检查反馈和实际现场状态；完成数只统计完成，并不排除部分运动。
