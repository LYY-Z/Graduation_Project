# 证据卡：电机热与负载感知的轮足运动（Go2-W）

> **主模型复核（2026-11-24）**：arXiv 2611.22231《From Temperature-Limited to Battery-Limited Legged Locomotion》（2026-11-17）和 arXiv 2606.21387《Long-Distance Real-World Navigation of the Legged-Wheeled Robot Go2-W Using Deep Reinforcement Learning》（2026-06-19）的题目与日期已核实。unitree_sdk2 主干 `include/unitree/idl/go2/MotorState_.hpp:32` 中有 `uint8_t temperature_` 字段，已核实。


核查日期：2026-11-24。问题导向方向，不是单篇论文。标记：**【事实】** 来自论文/仓库/文档原文；**【评价】** 本次评估者判断；**【猜想】** 未经验证的设想。

## 0. 先给结论

1. **Go2 上的热感知学习已被占据，且比粗筛判断的更密。** 粗筛说"热感知运动只在 A1 上做过"，现已过时：2026-11-17 出现 Go2 上的 Ségas 等（arXiv 2611.22231），在 Go2 实机上做了热网络辨识 + 热奖励 + 10 km 实机验证。Go2-W（有轮）上"温度进入策略训练"仍未见人做，但空档只剩"轮"与"髋关节负载"这一窄带。
2. **温度可读：** `unitree_go` 的 `MotorState_` 有 `temperature` 字段，Go2-W 官方示例用同一消息类型，Matsuzawa 等已在 Go2-W 实机上读取并记录温度。可靠性有保留：整数度、传感器有约 12 s 一阶滞后（Ségas 辨识值）、测点位置未公开、阈值未公开（论文估计 84–86 °C）。
3. **没有可直接复现的热感知基础论文**：六篇相关工作中没有一篇公开训练代码。可行路径是以 robot_lab Go2-W 为策略底座，自建热模型，方法上借鉴 Ségas（热奖励）或 Wan（残差）。
4. **推荐度：作为"主方向"勉强，不如作为"创新点模块"。** 见 §6。

### 1.3 查重相关的几点事实

- 【事实】**C 在 Go2 上已经把"实机辨识热网络 + 热奖励"做到 10 km 实机**，并明确把"调节指令速度的 governor"留作未来工作。C 还把 A、B 这类"温度进观测"的路线归入"启发式或温度奖励"类别，并以信用分配为由批评。（出处：2611.22231 abs/html）
- 【事实】D 明确说"温度难以并入学习过程"，所以没用；D 的相关工作提到"最近研究提出在仿真里直接建模发热并把温度放进策略训练"（即 A/B 一类）。D 与 A/B/C 是**独立**方向，未互相结合。
- 【事实】检索未发现任何在 **有轮** 平台（Go2-W、B2-W、Tron1、Diablo、M20、ANYmal-wheel）上把电机温度或热模型放入 RL 训练的论文。ATRos（2510.09980）的"节能"也只有奖励，无热。
- 【事实】检索未发现人形（G1/H1）上的学习式热控制论文；仅有 Apollo 的 MuJoCo 个人仿真仓库（I）和肌骨人形（G）。
- 【评价】A、B、C 三篇的热模型都是 **12 电机节点的腿式模型**，没有轮电机节点，没有"轮接触点在髋外侧导致持续外展力矩"这类 D 发现的结构性热源。这是 Go2-W 与 A1/Go2 的真实区别，也是仅剩的空档。
- 【评价】A、B、C 的实机验证都是单机、单载荷、基线是"无热项的同策略"，**没有一篇对比"固定降速 / 温度阈值降级"这类朴素方案**（A 的页面明确只有一个基线；B 的基线是 NLP 与 MTP；C 的基线是 DreamWaQ 及其加力矩惩罚版）。I 是唯一对比了朴素温度触发的工作，结论是朴素切换已很强。

## 2. 硬件可行性

### 2.1 `MotorState` 是否有温度字段（已核对源码）

| 位置 | 字段 | 类型 | 备注 |
|---|---|---|---|
| `unitree_sdk2`（C++）`include/unitree/idl/go2/MotorState_.hpp`，命名空间 `unitree_go::msg::dds_` | `temperature_` | `uint8_t` | 成员 ID 8；同结构还有 `mode_ q_ dq_ ddq_ tau_est_ q_raw_ dq_raw_ ddq_raw_ lost_ reserve_[2]` |
| `unitree_sdk2_python` `unitree_sdk2py/idl/unitree_go/msg/dds_/_MotorState_.py` | `temperature` | `types.uint8` | 同上 |
| `unitree_ros2` `unitree_go/msg/MotorState.msg` | `temperature` | **`int8`** | 与 SDK2 的 uint8 **不一致**（符号），温度在 0–127 内无差别 |
| `unitree_ros2` 的 `LowState` | 另有 `temperature_ntc1`、`temperature_ntc2` | — | README 未说明测点；那是 IMU/整机字段还是电机字段，本次未核到 |

- Go2-W 官方低层示例 `example/go2w/low_level/go2w_stand_example.py`（已打开）：从 `unitree_sdk2py.idl.unitree_go.msg.dds_` 导入 `LowState_`/`LowCmd_`，订阅 `rt/lowstate`，发 `rt/lowcmd`，循环周期 2 ms；该示例只读 `motor_state[i].q`，**没有使用温度**。但消息类型与 Go2 相同，温度字段随消息发出。
- **单位与分辨率：** 官方文档与源码均未写单位。证据：D 用"°C"报告 Go2-W 的 SDK 温度（84–86 °C 停机）；一篇日本开发者博文（Classmethod）读 Go2 `rt/lf/lowstate` 的 `motor_state[i].temperature`，待机 33–38 °C，推断为摄氏。**分辨率由整型决定，为 1 °C 级（推断）。** 该博文提示：uint8/int8 差异下，若读到 200 多的值需要手动 −256。
- **更新率：** 官方文档未给 `rt/lowstate` 或 `lf/lowstate` 温度的发布率。C 以 50 Hz 采样所有电机温度、每 2 s 记录统计；但这只说明 SDK 可被 50 Hz 轮询，**不说明传感器本身 50 Hz 更新**。unitree_ros2 README 说 `lf` 表示低频，具体频率未给。**必须实机用 `rt/lowstate` 测，才知道温度字段是否每帧变化。**
- **设置读取路径对 Go2-W：** 有 D 作为实机旁证：论文说温度来自机载传感器、力矩来自 SDK 估计。D 未说明是否读 `motor_state.temperature`，但同平台、同 SDK，【评价】极可能是。仍需到实机确认 16 个通道中哪些通道温度有效，**特别是 4 个轮电机**（D 只谈髋、膝，未给轮电机温度）。

### 2.2 读数可靠性

- 【事实】C 辨识出测量温度相对热网络节点状态的一阶滞后 τ_obs=12.2 s。这说明 Go2 的温度读数不是绕组温度，而是延迟约 12 s 的外壳/驱动板量。（出处：2611.22231）
- 【事实】博文：测点（定子/驱动板/外壳）"没有公开文档"。
- 【事实】D、C 均未报告传感器偏置或校准。**没有找到专门评估 Go2 温度读数精度的文献或社区报告**；检索范围为网页搜索，未查 Unitree GitHub issues 或官方论坛，这是缺口。
- 【评价】对于控制来说，12 s 滞后相对于热时间常数（分钟级）是可接受的，但对"接近阈值时的实时保护"不够快；整数度分辨率对"温升速率"信号（B 的奖励用温度变化率）噪声较大。

### 2.3 过热保护阈值与行为

- 【事实】官方：未找到公开数值（Unitree Go1 电机页只说有测温传感器与工作环境 −5～40 ℃，无阈值；Go2、Go2-W 无）。
- 【事实】社区/论文证据：C 写"Go2 约 86 °C 停机"；D 写停机约 85 °C（作者凭经验估计，厂商未公开），实测 84、86 °C 触发。**两篇都说是"机器人停机/停止"，没有说明是单电机失能、整机趴下还是断电。** 行为细节是缺口，实机前必须在安全设置下确认。
- 【评价】A/B 用的 60 °C 是奖励里的软上限，不是硬件阈值；若沿用 60 °C，则是 24–26 °C 的安全裕度，与 C 的"14 °C 裕度"做法同类。

### 2.4 仿真热模型与参数辨识

- 【事实】一阶热模型：热容 C、热阻 R、发热 = 电流²×绕组电阻（Qian 等 Eq.1；G 是两电阻模型）。A/B 的做法：用 RMS 力矩近似电流，14 节点网络；C：13 节点、22 参数。
- 【事实】C 证明在 Go2 上参数**可以从实机数据辨识**：4 小时 × 2 段训练 + 21 次验证/测试，RMSE <1 °C。B 证明 A1 上可以用最小二乘从"自然冷却 + 规定力矩 + 行走"辨识。
- 【评价】Go2-W 的辨识工作量：16 个节点（含 4 轮）、数据量 C 量级（数小时到十数小时连续实机运行，且需运行到较高温度，有风险）；滞后 12 s 的测量模型要同时辨识；轮电机的发热模型（速度环、反电势、机械损耗）与腿位置环不同，C 的"力矩²与速度"二次发热模型对轮是否充分未知。
- 【评价】Isaac Lab 里没有现成热模型执行器，需要自己在环境里加温度状态（每步更新节点温度），实现量不大（线性状态空间）。

| I Apollo | 有（MIT） | MuJoCo，与 Isaac 无关 | 人形上半身 | 只可借鉴热模型代码（`thermal/joint_model.py`）和"朴素温度触发切换"基线的评测思路 |

- 【结论】**没有合适的单篇热感知基础论文。**
- 【评价】可行组合：**策略底座 = robot_lab Go2-W（Isaac Lab 2.3.2，现有 `wheeled/unitree_go2w` 环境）+ rl_sar 部署**，LocoWM 或 MoE-CTS 的相关内容（见各自证据卡）可作为备选底座；**方法基础 = C 的"热网络 + 稳态温度奖励"**（不需要温度观测，因此部署侧最简单，不依赖温度读数的更新率与滞后）或 B 的"冻结名义策略 + 热残差"（与 LocoWM 的"冻结 + 残差"在结构上同类，若选 LocoWM 作底座则可以对接）。两者都需要从论文描述重新实现，无代码可对齐，**复现风险属于"无法对齐论文数字"而非"跑不起来"**。
- 【评价】论文第一步"复现"在此方向上基本只能是"复现现象"：先在自己的 Go2-W 上复现 D 的现象（厂商控制器或 robot_lab 策略行驶，测温升曲线），再复现 A/B/C 之一的方法效果。这与"选基础论文 → 对齐其结果"的流程不同，需要老师确认可否接受。

## 4. 研究空白与新颖性判断

逐项查重，结论基于 §1 的检索范围。

| 候选问题 | 已有覆盖 | 评价 |
|---|---|---|
| **a. Go2-W 上"热奖励 + 热模型"训练（含轮节点）** | 腿式已覆盖：A、B、C。轮足：未见 | 新颖性仅来自"平台特有的热结构"（轮接触点在髋外侧产生持续外展力矩，髋成为单热点）。**风险：评审可能看成 C 的平台迁移。** 如果不能证明轮足的热结构使方法必须改变（例如不能用 C 的步态平均稳态奖励，因为轮行驶接近准静态、没有步态周期），就只是迁移 |
| **b. 轮/腿负载分配以降热** | D 靠奖励间接诱导抬腿，降髋力矩到 0.4 倍，但没把温度当目标，也没分析"该多抬还是该多滚"的最优分配 | **相对未被做**：显式的"髋热 vs 总能耗 vs 速度"权衡与 Pareto 分析没见到。【评价】这是最贴近 Go2-W 的科学问题；但 D 已给出"周期抬腿能让系统稳在 60 °C"，增量需要证明比"D 的奖励设置"更好 |
| **c. 热状态下的模式切换（行驶↔抬腿散热↔越障）** | D 明确留作未解决（手动切换）；A 把"温度相关模式"列为未来工作；I 在人形上做了温度触发切换（仿真）；MUJICA、MoE-PPO 有技能选择器但与温度无关 | 未见轮足上温度驱动的模式选择。【评价】问题成立，但朴素的"温度 > 阈值则切换"在 I 中已很强，学习方法的价值需要比较后才知道 |
| **d. 热模型在线辨识** | G 在肌骨人形上在线学习热参数；A/B/C 离线辨识；Go2-W 未见 | 【评价】对本科周期偏重：需要长时间升温实机数据；C 已证明离线辨识 <1 °C 误差，在线辨识的边际收益（载荷/环境温度变化）需要证据。可作可选扩展 |
| **e. 指令速度 governor（据预测热状态调速）** | C 把它列为未来工作；I 的预测规划器反而不如温度触发 | 未见实机做。【评价】但这是"简单替代方案"的同类，若做成学习式要证明胜过阈值降速 |
| **f. 载荷与热的联合（8 kg 官方载荷）** | A/B 3 kg，C 5 kg，均腿式 | 轮足带载荷升温的数据未见；与 a 合并 |

### 简单替代方案能不能解决

- 【事实】朴素方案有三类：(i) 固定降速/降功率；(ii) 温度阈值降级（接近 T_thr 时按线性比例降低指令速度或停车散热）；(iii) D 式"无温度的奖励诱导抬腿"。D 的 (iii) 已在 Go2-W 上把平地行驶稳在约 60 °C，51 分钟不停机。
- 【事实】I 在人形仿真里"温度触发切换"≥"预测式规划"，且它自己撤回了早先"比反应式降额好 41%"的说法，因为缺公平基线。
- 【评价】**尚没有任何证据表明学习式热感知在轮足上明显优于 (ii) + (iii) 的组合。** A/B/C 都没与 (ii) 对比。因此本方向的第一个实验应是：在 Go2-W 上量化"(iii) + 速度阈值降级"能把续航推到哪里（是否已达到电池耗尽，如 C 的 174 分钟那样）。若已达到，学习式热感知的增益空间只剩下"任务速度更高、越障与散热同策略"。
- 【评价】不预设学习更好。学习的真正附加价值只可能在：同一策略内联合处理"热—越障—速度"（D 所说无法在单策略完成的问题），而不是单纯提升续航。

### 实机验证方案与风险

- 指标：长时间行驶中 16 通道温度曲线（含 4 轮）、停机/触发保护次数、平均速度、距离与 COT（BMS 可读电池，见 go2w.CN.md）、任务成功率（越障）、起始温度与环境温度记录。需控制起始温度（A 承认户外起始温度不可比）。
- 实验设计：同载荷、同地面、同起始温度，对比 (1) 厂商控制器，(2) robot_lab 基线策略，(3) 基线 + 阈值降速，(4) 本方法；每组重复。
- 风险：
  1. **电机过热损坏。** 要把硬阈值留在软件侧（如 70 °C 人工终止，远低于约 85 °C 停机），不要做"跑到停机"的实验。D 做过停机实验，我们不应复制。
  2. 保护触发时的机器人行为未知（趴下？断电？）。可能在行驶中失控或摔落；需围栏、低速、人工急停。
  3. 温度读数滞后 12 s：在阈值边缘保护不够快。
  4. 单机资源：一次升温到 60 °C 约需 30–40 分钟（D），冷却同样慢，一天的实验次数有限；只有有限重复数，统计强度弱。
  5. 轮电机的温度可读性与热模型未知，可能整个"轮"这条线最先被卡住。
- 工期：热模型辨识（≥ 数小时实机）+ 环境改造 + 训练 + 部署 + 多组长时间实机，3–4 个月偏紧；实机阶段主要受"每次长实验耗时"限制，而非算力。

## 5. 研究猜想（均为猜想，未验证）

- 猜想 1：Go2-W 的 16 节点热模型中，髋节点的发热来自"轮接触点偏离髋轴"产生的持续外展力矩，可用一个与步态周期无关的"静态外展力矩"项解释；据此可以不依赖步态周期的热代价（区别于 C 的步态平均）。
- 猜想 2：热状态条件化的单策略（观测含温度或预测稳态温度）在冷态偏效率/速度、热态自动增加抬腿，可取代 D 的人工切换。需要先证明 D 的抬腿策略在越障时确实不能同时满足散热（D 的陈述，非我们复现）。
- 猜想 3：用 C 的"不观测温度、仅用预测稳态温度作奖励"路线，再叠加一个部署端的轻量速度 governor（阈值式），比"温度进观测"更稳健，因为避开了读数滞后。

## 6. 总体判断

**推荐度（评价）：不建议作为唯一主方向；建议作为"有条件的创新点"，并先做两个低成本验证。**

理由：
1. 动机真实且具体（D 的实机报告），温度读数在 Go2-W 上存在；这是优点。
2. 但 Go2 上已有 C（实机辨识、热奖励、10 km 实机），A/B 在 A1 上占了观测与残差路线。轮足上的空档窄，且最容易被评审看作"C 的平台迁移"。
3. 没有可复现的基础论文，复现链条要靠自己重写，且实机实验耗时长、有硬件风险。

**最大的三个不确定项：**
1. **Go2-W 的 16 路温度（尤其 4 个轮电机）是否可靠可读**，更新率与测点如何；轮电机的热模型能否用腿的二次发热模型近似。这决定整条"轮"线能否成立，可在实机上用 1–2 小时只读采集先证实。
2. **朴素方案（阈值降速 + D 式奖励诱导抬腿）是否已足够**。若足够，学习式热感知的增量只剩"单策略同时散热与越障"，创新量不足以撑起主方向。
3. **新颖性是否站得住**：评审是否把"Go2-W + C 的热奖励"看作迁移；能否证明轮足的热结构迫使方法发生实质变化（见 §4 a）。另有投稿方面的不确定：C 已投 IEEE，同期竞争激烈。

**建议的下一步（均不触碰硬件控制）：** (1) 只读采集 Go2-W 的 `motor_state.temperature`，确认 16 通道与更新率，行驶中的温升；(2) 在 robot_lab 中给基线策略加简单阈值降速，对比 D 的数字；(3) 若 (1)(2) 都支持，再决定是否将"热感知"并入 LocoWM/MoE-CTS 底座作为创新模块。
